# 探索訪談與盤點工作簿

## 目的與狀態

優先驗證「文件版本與證據追溯」，同時收集一般專案、部門流程、跨部門流程及受監管情境的共同需求與差異。本工作簿是執行材料，不代表訪談已完成。每項結論須附來源、日期、受訪角色和確認狀態。

## 角色抽樣與訪談

每個首輪流程至少邀請：流程擁有者／部門主管、實際執行者、專案經理、QA／獨立審查者、文件控制人員、IT／資安／資料治理代表。受監管情境另邀請法遵或法規負責人。先個別訪談執行者，再共同走查流程，降低主管流程圖取代實際作業的風險。

每場訪談記錄：日期、部門、角色、匿名代碼、流程、資料來源、觀察到的事實、受訪者主張、推論、未確認事項、待驗證證據、核對人。區分 `observed`、`reported`、`inferred`、`unconfirmed`；未經證據核實的敘述不得升格為政策或合規要求。

### 訪談問題

1. 這項工作由什麼事件啟動？誰提出、誰負責、誰會受影響？請最近一次實例逐步說明。
2. 每一步使用哪些系統、表單、文件、群組或口頭決策？資料在哪裡建立、修改、簽核及封存？
3. 如何辨識正式有效的文件版本？實際遇到過哪些重複、過期、無權限、連結失效或核准缺失？
4. 哪些證據能證明工作已完成、由誰完成、依據哪一版規範、何時核准？稽核時如何找到它？
5. 哪些工作會退回、例外放行、升級或跨部門等待？通常由誰決定，等待多久？
6. 需求、風險、變更、缺失及矯正措施如何互相追蹤？何時可以關閉？如何確認措施有效？
7. 哪些欄位或步驟可標準化？哪些必須由部門自訂？不可豁免的法律、安全、隱私或合約要求有哪些？
8. 哪些資料可供 AI 處理？哪些必須遮罩、留在租戶內、完全禁止？AI 草稿由誰審查和核准？
9. 如何判斷新流程成功？請提供可取得的分子、分母、時間戳或既有報表，並指出資料品質限制。

## 工具與資料清冊

每個系統記錄：產品／租戶／擁有者、用途、來源系統或權威來源、資料類型與敏感級別、身分登入及群組、版本／簽核／留存能力、API／匯出能力、授權與連接器權限、稽核日誌、備份／復原、資料所在地限制、限制與替代方案。涵蓋 Microsoft 365、Google Workspace 及訪談發現的混合工具；不得先假設已購買特定授權或 API 權限。

## 試點選擇與決策

以文件追溯痛點明確、具跨部門交接、流程擁有者可投入、可取得非敏感測試資料、系統權限可核實、可在一個週期內觀察結果為選擇條件。受監管流程可以參與共通需求探索；首輪試點只在法遵代表確認通用控制足以試驗後採用，否則改選一般商業流程。

試點開始前，由業務負責人核准：範圍、角色、資料分類、來源系統、指標定義與目標、例外規則、成功門檻、停止條件。既有工具可達標時產出可複用模板；若仍有經核准的關鍵缺口，記錄影響、替代方案成本與平台建置決策，不能由工程團隊自行假設已通過建置門檻。
