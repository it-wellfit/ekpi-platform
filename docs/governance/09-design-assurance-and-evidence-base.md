# 設計保證、需求品質與研究依據 v1.0

**用途：** 把本套件的設計決策繫結至可公開查證的標準、權威指引與同儕審查研究，並規定需求品質、變更影響、驗證方法、敏捷進版及市場比較方法。標準交叉參照是設計依據，不代表組織已符合或獲認證；若要主張特定產業法規符合，須由相應法遵人員以適用的授權標準版本做逐條評估。

**研究盤點日期：** 2026-10-25。研究盤點採結構化範圍，而非宣稱窮盡全世界所有文獻／商品。優先標準原文、制定機構官方頁、權威研究機構全文與同儕審查系統性回顧；搜尋字詞、日期、納入／排除與決策須保存在本文件的更新紀錄中。

## 2. 需求原子格式與品質 gate

### 需求資料列（所有 SHALL／MUST 都須有下列屬性）

| 屬性 | 必填內容 |
| --- | --- |
| `requirement_id` | 永不重用的穩定 ID；文字修訂不換 ID，刪除以 deprecated 標記 |
| `statement` | 一個可測的行為／品質主張，指出系統主體、條件／觸發、輸入、可觀察結果與限制 |
| `need_source`／`parent_id` | 受訪者角色／證據參照、業務需求或更高階需求的向上追溯 |
| `rationale`／`owner` | 為何需要、誰負責解釋與核准 |
| `priority`／`scope` | MoSCoW 或 P0/P1/P2 範圍決定及版本理由；不可只寫 must-have 而沒有發布版 |
| `preconditions`／`business_rules` | 權限、資料、狀態、時間、例外與不可豁免規則 |
| `acceptance_criteria` | 一個或多個 GIVEN／WHEN／THEN，至少含正常、拒絕／錯誤及邊界路徑 |
| `verification_method` | 檢視／分析／示範／測試／稽核等實際可行的驗證方法、測試 ID 與預期證據 |
| `design_links` | 服務／頁面／資料實體／狀態轉移／API 介面／威脅或 UX 決策 |
| `risk_quality_tags` | 安全、隱私、可用性、性能、可存取性、稽核、資料保留或其他適用品質屬性 |
| `dependencies_assumptions` | 依賴、假設、待決 ID；待決值不能藏在句子或預設資料裡 |
| `baseline_version`／`change_history` | 版本、狀態、核准、有效日期及變更影響 |
| `implementation_release`／`verification_result` | sprint/release、PR/commit/build、測試結果、缺陷與重測證據 |

### 通過需求品質檢查的硬條件

每條需求都必須同時通過下列檢查；不能用平均分數掩蓋單條不合格：

1. **必要且有來源：** 若移除會失去哪項業務能力／控制？有證據、明確決策或上層需求支持。
2. **適當且不偷塞解法：** 說明所需結果，不在業務需求層無理限定框架／供應商；需限定時記錄技術／法規理由。
3. **單一：** 一條主要陳述只要求一個可獨立驗收行為；條件可多個但拆分的失敗狀況要能各自判定。
4. **明確／完整／一致：** 詞彙表有定義；輸入、前置狀態、權限、成功與拒絕結果、相關物件、例外和適用情境都已說清楚；同一概念各文件一致。
5. **可行且必要：** 架構、租戶能力、法令和資料存取可行性已驗證；依賴已追蹤。
6. **可驗證：** 有觀察方法、客觀判定準則和測試證據；避免「直覺、完整、快速、容易、業界最佳」等無量尺用詞。
7. **可追溯／可改版：** 找得到來源、父需求、設計物件、測試與發布；變更能計算受影響項目。

詞彙政策：以「當 `[前置條件]`，系統 MUST 在 `[觸發]` 後於 `[可核對情境]` 產生／拒絕 `[結果]`」寫需求。數值門檻要帶量測方法、百分位、樣本量、資料範圍與環境。沒核定時以 `TBD-DEC-nn` 明確標示，並禁止相關發版 gate 以通過替代。

### Definition of Ready（進入 Sprint）

故事／需求具唯一 ID、業務來源和受訪角色確認、使用者／受影響角色、主路徑與至少一個例外、資料分類／權限影響、關聯狀態／API／UX 原型、Given-When-Then 驗收、NFR／安全／無障礙影響、依賴及未決事項。阻擋該故事驗收的決策已核准。Sprint 團隊估算後可以完成；大型項目先拆垂直可展示切片。

### Definition of Done（故事／迭代完成）

需求追溯完整；設計／ADR 與資料字典更新；服務端授權和狀態不變條件實作；程式審查通過；適用單元、屬性、整合、API contract 與端到端測試通過；安全／依賴掃描結果處理；介面完成鍵盤／輔助科技／響應式檢查；遷移、稽核、監控、錯誤與操作手冊更新；測試證據關聯 commit/build；沒有未核准的硬編碼政策。

## 3. 雙向追溯與變更影響

```text
真實工作事例／訪談／政策／法規來源
      ↓ NEED → BUSINESS REQUIREMENT → SYSTEM FR/NFR → DESIGN/ADR/API/STATE/DATA → STORY/COMMIT
      ↑                                                                                 ↓
      └────────── 價值與實際使用驗證 ← ACCEPTANCE/TEST/EVIDENCE ← RELEASE ← IMPLEMENTATION
```

追溯存為有方向的關聯圖，至少辨識 `derived_from`、`satisfied_by`、`verified_by`、`implemented_by`、`constrained_by`、`impacted_by`、`supersedes`。每個發版出具完整性報表：沒有來源的需求、沒有實作的必要需求、無測試／無結果需求、孤兒設計、變更影響未審查項都列明。狀態版本不可覆寫，修改者須用新版本與決議說明。

需求變更需建立 Change ID，至少評估上游原因、受影響需求／模板／在途執行／資料遷移／測試／訓練／連接器／角色／法規、回溯適用性、停機／回退、利益／風險；變更核准後更新基線並建立具名遷移任務。已發布流程不因最新需求版改變而靜默更新。

### 推薦產品 UX 發版基準

- 最低可用寬度 320 CSS px；頁面支援 200% 縮放；主要操作不依 hover；所有功能可鍵盤完成。
- 正式產品的 WCAG 基線定為 2.2 AA；先由 UX／IT 確認當地政策，若法規或合約指定更嚴則從嚴。
- 任務測試以代表性角色腳本（建立專案、連結正確版文件、退回補件、處理 QC 缺失、作 gate 決議、尋找稽核證據）記成功／失敗、未受協助完成率、耗時、錯誤和信心；不以主觀「看起來專業」取代觀察。

## 5. 完整 V&V 證據策略

驗證「建置對了」（verification）和確認「建置的是正確產品」（validation）分開簽核。每種方法須先指定哪些需求可用該方法驗證、環境、工具／版本、資料、通過門檻、證據保存位置和獨立審查角色。

| 層次／方法 | 回答的問題 | 需保存的證據 | 本產品適用案例 |
| --- | --- | --- | --- |
| 需求檢查／稽核 | 句子完整、可測、互不衝突、來源可信嗎？ | 檢查清單、評審意見、需求版次與決議 | 預防模糊需求、孤兒需求、舊標準引用 |
| 業務走查／情境模擬 | 真實角色能否用規格完成工作？ | 工作坊角色／案例、目前／未來流程、問題與簽核 | 12 階段和退回／例外／跨部門交接 |
| UX 可操作原型／可用性測試 | 角色是否看得懂、做得完、能發現阻擋？ | 原型版、任務腳本、錄影／觀察（經同意）、量化結果 | 待辦、證據核查、關卡和 CAPA 端到端 |
| 分析／設計檢查 | 資料、狀態、架構或權限有矛盾／缺口嗎？ | 狀態表、資料字典、ADR、攻擊面圖、風險紀錄 | Gate 不變條件、租戶隔離、來源版本更新 |
| 靜態／形式檢查 | 可否由機械規則找出違規或不可達狀態？ | lint、型別／schema 驗證、規則覆蓋、模型檢查 | enum、ID 外鍵、狀態非法轉移、死鎖／循環 |
| 單元／屬性測試 | 純函式及不變條件對邊界值是否成立？ | case／seed、執行結果、coverage（依風險） | 關卡判斷、冪等、指標分母、日誌 hash |
| Contract／整合測試 | API、connector、身分系統是否符合雙方契約？ | OpenAPI/schema、虛擬來源結果、真租戶核准環境證據 | 401/403/409、權限撤銷、429、版本差異 |
| 系統／端到端測試 | 使用者旅程和跨元件狀態是否完整？ | 測試資料、操作結果、事件時間線、缺陷 | AT-01…AT-28 |
| 安全／隱私測試 | 攻擊者能否跨租戶、竊權、注入、洩漏或破壞事件？ | Threat model、OWASP ASVS 版本化項目、SAST/DAST/SCA、滲透報告、修正重測 | IDOR、提示注入、惡意 URL、敏感日誌、管理員濫權 |
| 效能／可復原測試 | 峰值、故障、備份、還原是否達成核准目標？ | 負載腳本、指標、故障／復原記錄及 RPO/RTO | 大專案查詢、報表、connector outage、事件重播 |
| 無障礙／跨裝置測試 | 符合 WCAG 2.2 AA 基線，且實際任務可用嗎？ | 工具掃描 + 人工準則檢查 + 受影響使用者任務觀察 | 鍵盤、讀屏、焦點、放大、錯誤、非顏色狀態 |
| 試點驗證／驗收 | 是否解決實際問題、指標是否改善且可持續？ | 前後相同口徑資料、限制／樣本偏差、使用者回饋、業務簽認 | 試點 go/no-go、MVP 決策 |

最低驗收原則：高風險需求至少用一項直接驗證方法加一項獨立證據交叉確認；每項安全／不可豁免控制至少有一個嘗試違規的負面測試；AI 風險需驗正常輸入、缺資料、矛盾、提示注入、錯誤與模型不可用；所有 FAIL 先修正並以原案例重測，仍要做受影響回歸。

## 7. 市場比較與「領先」主張的證據規則

沒有一套合理方法能證明某產品「勝過市場上所有軟體」：產品集合持續變動，涵蓋範圍與法規情境不同，未取得的產品／租戶也無法等條件驗證。因此不使用絕對領先主張。若要判定此解決方案相對現行工具和候選商品是否更合適，須先預註冊候選集合和任務腳本。

### 候選集合選取

1. 以現有 M365、Google Workspace、混合工具作 baseline；不忽略現行方案的設定成本和人工控制。
2. 依採購市場／業務用途選 3–5 個具代表性的候選（一般專案協作、文件／工作流、品質／GRC／企業流程），記錄納入理由、版本、SKU、地區及資料日期；由業務／採購確認 shortlist，而非由工程師暗中選供應商。
3. 官方文件只證明宣告／文件化的功能；必要控制須在試用租戶、合約、管理介面或實際 demo 驗證。第三方評論作為問題線索，不作控制能力證據。

### 同條件比較指標

用相同匿名樣本、權限角色、流程任務、測試期限與評分者比較：必要需求覆蓋／不可豁免控制、文件版次追溯完整度、設定到可用流程的實際工時、關卡阻擋正確性、跨部門待辦可見性、失效復原時間、稽核重建時間、角色任務完成率／錯誤、WCAG 適用成功準則、匯出／退出完整性、授權／整合／運維三年總成本及依賴風險。報每個指標原始數值、樣本量、誤差／限制及 evidence ID。

加權分數僅可在業務核定權重後作輔助；任何不可豁免需求未達即列為 fail，不可被其他高分平均掉。結論用「在指定試點任務與條件下，比 X 改善了 Y（樣本 N，日期，證據）」，不推廣成「超越所有產品」。採購市場和方案版號變更時重跑高風險比較。
