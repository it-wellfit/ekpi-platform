- **狀態：** Active（規劃基準；實作以切片推進，每片 canonical 收口）
- **Owner：** Product + Engineering
- **最後審閱：** 2026-11-06
- **定位聲明：** 「部門業務／API 中樞與資料管理／治理稽核」三個工作室是**起點不是答案**。本文件以第一性原理抽出不變需求，再把口號轉成可量測切片。市場痛點清單為**待驗證假設**（需 `DEC-01` 試點佐證），不得當作已驗證事實對外宣稱。

## 1. 第一性原理：從口號還原的四個不變需求

任何企業治理/營運軟體，無論市場包裝如何，其不可再化約的需求只有四項：

| # | 不變需求 | 反面（失敗態） | 本平台現有機制 |
|---|---|---|---|
| N1 可歸因 | 每個變更都能回答「誰、何時、依據什麼」 | 幽靈修改、代簽爭議 | session actor、hash-chain 帳鏈、審計頁 |
| N2 可回溯 | 每個結論都能回到來源原始位置 | 黑箱 AI、無錨判決 | doc@version§section 引用、H-4 錨定門檻 |
| N3 可防錯 | 未知≠允許；壞資料拒收而非降級 | fail-open、靜默錯誤 | fail-closed 讀取、拒載竄改、501 誠實邊界 |
| N4 可演進 | 規則/流程/介面可換而不動骨架 | 匯出鎖定、廠商鎖定 | 檔案即契約（JSONL/JSON）、契約文件、雙軌儲存 |

**設計律：** 任何新功能若削弱 N1–N4 任一項，即退回——這是「超越」的唯一安全底座。市場上多數產品的差異在功能面，勝負歷史反覆證明在**不變需求的實現深度**（可稽核、可匯出、可解釋）。

## 2. 市場痛點假設清單（待試點驗證；不宣稱調研結論）

| 痛點假設 | 族群 | 現有緩解 | 驗證方式（DEC-01 試點） |
|---|---|---|---|
| 資訊碎片化：文件散落 5+ SaaS，找不到「現行版本」 | 全體 | 版本化文件庫＋檢索頁 | 試點任務完成時間對照 |
| 審批黑箱：不知道卡在誰、為何卡 | 主管/申請人 | 核准佇列＋SLA 計＋階段點 | 佇列停留時間分布 |
| 稽核舉證成本：每季手工拼證據 | 稽核/品保 | hash-chain＋事件時間軸 | 舉證準備工時對照 |
| 工具孤島：匯出被鎖定 | IT/資料 | 檔案即契約＋bundle | 匯出/還原演練 |
| 權限蔓延：離職帳號仍在動 | IT 安全 | 本機 session＋actor 綁定（試點範疇） | Phase B IdP 缺口明列 |
| SLA 失控：逾期無人知 | 流程 owner | SLA 計＋逾期紅標（視覺） | 逾期率前後對照 |

## 3. 架構：一核心、三工作室、四橫切

```
                    ┌──────── 橫切：資安 / 可觀測 / 備份還原 / 契約治理 ────────┐
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│ A 部門業務   │  │ B API 中樞   │  │ C 治理稽核   │
│ 工作室       │  │ 與資料管理   │  │ 工作室       │
└──────┬──────┘  └──────┬──────┘  └──────┬──────┘
       └──────── 共用確定性核心（engine/rules/processes/retrieval）────────┘
       └──────── 雙鏈（治理 ledger + 核准 store）＋ RBAC ＋ 零 JS 呈現 ────┘
```

**A 部門業務工作室**（已奠基：工作流、核准、專案、證據、品質事項）
- 客製化：表單/階段/條件由定義驅動（domain 已型別化）
- 待建：佇列視圖（我簽核的/我申請的）、SLA 行事曆、行動後回饋微文案

**B API 中樞與資料管理**（已奠基：唯讀契約 CTR-API-001、decisions export v2）
- SDD 先行：寫入契約（冪等鍵、重放防護）→ webhook 出站 → 資料地圖（欄位級血緣）
- 資安演進：工作階段輪替、金鑰生命週期；企業 WORM/IdP 屬 Phase B（DEC-12/13）

**C 治理稽核工作室**（已奠基：稽核頁、鏈徽章、證據包匯出片段）
- 深化：控制矩陣視圖、合規報告產生器（以 decisions export 為底）、稽核包（bundle+manifest）

## 5. 「超越」的量測語言（不宣稱打敗任何產品）

超越不是形容詞，是量測：試點中以**同任務基準線**比較（完成時間、人工交接次數、錯誤率、舉證工時）。未能量測前，一律使用「本機示範可用」而非「領先/最強」。此條為誠實鐵律（AGENTS.md）之直接推論。
